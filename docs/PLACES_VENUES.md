# 플레이스 탐색: 여기서 열리는 팝업

## 구현 범위

- `app/pages/places.vue`의 탐색 탭에서 `PlacesEndingSoon` 바로 아래에 `PlacesVenues`를 표시한다.
- PC는 3장·간격 16px, 모바일은 1장과 터치 스와이프를 제공한다. 기존 Embla를 사용하며 무한 반복하지 않는다.
- 이미지 비율은 1.55:1, 모서리는 12px이다. 이미지 오른쪽 위에 실제 API 개수 배지를 표시한다.
- 전체 탭·검색·필터·홈·지도·기존 곧 끝나요 컴포넌트는 변경하지 않는다.

## 데이터 출처와 집계

읽기 전용으로 확인한 앱의 `src/lib/popupVenues.ts`, `src/components/home/HomeVenueSection.tsx` 및 백엔드 `PublicPopupService.java`, `PublicPopupMapper.xml`의 기존 계약을 따른다.

| 항목 | 기존 데이터 및 기준 |
| --- | --- |
| 목록 | `GET /api/popups/venues?languageCode=ko`의 `venues` |
| 식별 | API가 제공하는 `venueId`(등록 장소의 `venue_key`) |
| 장소명·주소 | 등록 장소의 `name`, `address` 그대로 사용 |
| 대표 이미지 | 관리자가 등록한 `popup_venues.image_key`로 발급된 API의 `imageUrl` |
| 개수 | 공개 팝업 API의 `popupCount`, SQL의 `COUNT(DISTINCT p.id)` |
| 장소 매칭 | 등록 장소와 팝업의 주소가 바이너리 비교로 완전히 같아야 함 |
| 진행 조건 | `type=POPUP`, 오늘 진행 중 또는 오픈 예정, 종료일이 지난 팝업 제외 |
| 정렬 | 기존 API의 등록 장소 생성일 내림차순 유지 |

주소 공백 제거, 부분 문자열, 좌표 근접도 등을 이용해 서로 다른 장소를 임의로 합치지 않는다. 웹에서 별도 공개 상태를 추정하지 않고 기존 공개 API의 노출 계약을 사용한다.

진행 중은 시작일 ≤ 오늘 ≤ 종료일이다. 예정 팝업은 시작일 > 오늘이면서 종료일이 없거나 오늘 이후인 경우다. 앱·백엔드의 기존 집계를 재사용하며 웹의 날짜 기준은 한국·일본 공통 UTC+9다.

대표 이미지가 없거나 로드에 실패하면 안내를 표시한다. 외부 대체 이미지를 만들거나 가져오지 않는다.

## 요청·캐시·SSR

- Nuxt의 읽기 전용 중계 경로: `GET /api/places/venues` 및 선택 시 `?venueId=...`.
- Spring의 기존 API만 호출하며 백엔드 엔드포인트·DB는 변경하지 않는다.
- 최초 SSR에서 장소 목록 한 번을 읽고 `useFetch` payload를 재사용한다. 장소마다 개수를 조회하는 N+1 요청은 없다.
- 장소를 선택한 경우에만 같은 기존 API에 `venueId`를 전달해 그 장소의 전체 팝업을 조회한다. 페이지네이션 목록을 전체 개수로 간주하지 않는다.
- Nitro 캐시는 API Base URL·날짜·장소 ID별 30초, SWR 없음이다. 브라우저에서도 선택한 장소의 응답을 30초 재사용한다.
- 활성 탭에서만 3분 경과 또는 UTC+9 날짜 변경 시 목록을 갱신한다. 이미지 만료 복구는 기존 곧 끝나요와 같은 제한된 방식이다.
- 잘못된 응답·개수 불일치는 오류로 처리하고 0개로 바꾸지 않는다. 팝업 목록은 publicId로 중복 제거하며 API 개수와 일치하는지 확인한다.
- 요청에 인증 정보·쿠키를 전달하지 않으며 임의 URL 프록시를 제공하지 않는다.

## 카드 선택

현재 웹에는 재사용할 장소별 목록 라우트가 없고 전체 탭의 검색·필터 변경은 요청 범위 밖이다. 새 페이지를 만들지 않고 이 섹션 내부의 네이티브 대화상자로 해당 장소의 팝업을 표시한다.

- 카드 선택: 현재 `/places` 안에서 장소별 팝업 목록 열기.
- 팝업 선택: 기존 `/places/{publicId}` 상세 페이지로 이동.
- 닫기·Escape·포커스 복귀 및 조회 실패 시 재시도를 제공한다.

## 실제 데이터 확인 결과

2026-10-26 확인 시 운영 `GET /api/popups/venues?languageCode=ko` 응답은 정상 `{"venues":[]}`였다. **실제 표시 가능한 장소는 0개**이며 화면에 빈 상태 안내를 표시한다.

공개 응답만으로는 등록 장소 자체가 없는지, 주소가 정확히 일치하는 진행·예정 팝업이 없는지 구분할 수 없다. 임의 장소·이미지·개수를 추가하지 않았다. 실제 장소 카드와 대표 이미지의 최종 확인에는 기존 장소 API가 실제 장소를 반환해야 한다. 유효한 장소 ID가 없어 운영 장소별 팝업 API는 호출하지 않았다.

## 검증

- `npm run typecheck`, `npm run build` 통과.
- 실제 빈 장소 응답으로 SSR 200·빈 상태 표시·장소 목록 요청 1회·장소별 요청 0회를 확인했다.
- 응답 정규화에서 주소 보존, ID 중복 거부, publicId 중복 제거, 진행·예정 날짜, 전체 개수 불일치·오류 처리를 확인했다.
- **별도 검증용 계약 응답**으로 PC 3장(너비 약 264.66px·간격 16px), 모바일 1장(335px), 이미지 비율, 스와이프, 유한 화살표, 모달, 상세 링크, 닫기·Escape, 404 안내, 캐시 재열기를 확인했다.
- 동일 검증에서 Hydration 완료 후 초기 브라우저 API 요청 0회, 장소 선택 시에만 조회, Hydration mismatch·미처리 예외 없음, 모바일 가로 넘침 없음을 확인했다.
- 검증용 응답은 제품 코드에 포함하지 않았다. 실제 장소가 채워진 운영 데이터 검증과는 구분한다.
