# 플레이스 탐색: 여기서 열리는 팝업

## 구현 범위

- `app/pages/places.vue`의 탐색 탭에서 `PlacesEndingSoon` 바로 아래에 `PlacesVenues`를 표시한다.
- PC는 3장·간격 16px, 모바일은 1장과 터치 스와이프를 제공한다. 기존 Embla를 사용하며 무한 반복하지 않는다.
- 이미지 비율은 1.55:1, 모서리는 12px이다. 이미지 오른쪽 위에 실제 API 개수 배지를 표시한다.
- 전체 탭·검색·필터·홈·지도·기존 곧 끝나요 컴포넌트는 변경하지 않는다.
- 장소 카드는 모달 대신 `/venues/{venueId}`의 독립적인 장소 상세 페이지로 연결한다. 컴포넌트 사용처는 `/places` 한 곳이며, 해당 컴포넌트의 모달·열기/닫기·포커스 복귀·선택별 브라우저 캐시·모달 CSS를 제거했다.

## 데이터 출처와 집계

읽기 전용으로 확인한 앱의 `src/lib/popupVenues.ts`, `src/components/home/HomeVenueSection.tsx` 및 백엔드 `PublicPopupService.java`, `PublicPopupMapper.xml`의 기존 계약을 따른다.

| 항목 | 기존 데이터 및 기준 |
| --- | --- |
| 목록 | `GET /api/popups/venues?languageCode=ko`의 `venues` |
| 식별 | API가 제공하는 `venueId`(등록 장소의 `venue_key`) |
| 장소명·주소 | 등록 장소의 `name`, `address` 그대로 사용 |
| 대표 이미지 | 관리자가 등록한 `popup_venues.image_key`로 발급된 API의 `imageUrl` |
| 개수 | 공개 팝업 API의 `popupCount`, SQL의 `COUNT(DISTINCT p.id)` |
| 장소 매칭 | 등록 장소와 팝업의 주소가 바이너리 비교로 완전히 같아야 함 |
| 진행 조건 | `type=POPUP`, 오늘 진행 중 또는 오픈 예정, 종료일이 지난 팝업 제외 |
| 정렬 | 기존 API의 등록 장소 생성일 내림차순 유지 |

주소 공백 제거, 부분 문자열, 좌표 근접도 등을 이용해 서로 다른 장소를 임의로 합치지 않는다. 웹에서 별도 공개 상태를 추정하지 않고 기존 공개 API의 노출 계약을 사용한다.

진행 중은 시작일 ≤ 오늘 ≤ 종료일이다. 예정 팝업은 시작일 > 오늘이면서 종료일이 없거나 오늘 이후인 경우다. 앱·백엔드의 기존 집계를 재사용하며 웹의 날짜 기준은 한국·일본 공통 UTC+9다.

대표 이미지가 없거나 로드에 실패하면 안내를 표시한다. 외부 대체 이미지를 만들거나 가져오지 않는다.

## 요청·캐시·SSR

- Nuxt의 읽기 전용 중계 경로: `GET /api/places/venues` 및 선택 시 `?venueId=...`.
- Spring의 기존 API만 호출하며 백엔드 엔드포인트·DB는 변경하지 않는다.
- 최초 SSR에서 장소 목록 한 번을 읽고 `useFetch` payload를 재사용한다. 장소마다 개수를 조회하는 N+1 요청은 없다.
- 장소를 선택한 경우에만 같은 기존 API에 `venueId`를 전달해 그 장소의 전체 팝업을 조회한다. 페이지네이션 목록을 전체 개수로 간주하지 않는다.
- Nitro 캐시는 API Base URL·날짜·장소 ID별 30초, SWR 없음이다. 상세 페이지도 같은 중계 API와 캐시를 재사용하며 API 응답 형식은 변경하지 않는다.
- 활성 탭에서만 3분 경과 또는 UTC+9 날짜 변경 시 목록을 갱신한다. 이미지 만료 복구는 기존 곧 끝나요와 같은 제한된 방식이다.
- 잘못된 응답·개수 불일치는 오류로 처리하고 0개로 바꾸지 않는다. 팝업 목록은 publicId로 중복 제거하며 API 개수와 일치하는지 확인한다.
- 요청에 인증 정보·쿠키를 전달하지 않으며 임의 URL 프록시를 제공하지 않는다.

## 독립적인 장소 상세 페이지

- 구현: `app/pages/venues/[slug].vue`. 내부 식별자는 공개 API의 `venueId`(불변 `venue_key`)를 유지하고, 공개 URL만 `shared/utils/venueRoutes.ts`의 검증된 고정 매핑을 사용한다. 이름 변경이나 요청 시 번역으로 slug를 다시 만들지 않는다.
- 사용자 확인된 더현대 서울 ID `venue-36bf5330-7454-4ebc-9038-ff5448fb414f`를 `the-hyundai-seoul`에 매핑한다. 최종 URL은 `https://theplave.co.kr/venues/the-hyundai-seoul`이다. 다른 장소는 확인되지 않아 추가 매핑하지 않았다.
- 초기 SSR에서 기존 `/api/places/venues`와 `?venueId={실제 venueId}`를 병렬로 기다린다. 장소명·주소·팝업명·기간·태그·상세 링크를 HTML에 출력하며, Nuxt payload를 hydration에서 재사용한다. 팝업별 상세 조회는 하지 않는다.
- 팝업은 기존 API 순서(`p.created_at DESC, p.id DESC`)와 진행·예정만 포함하는 정책을 유지한다. 성공한 0개 응답은 빈 상태를 표시한다.
- 현재 공개 장소 목록은 팝업이 1개 이상인 장소만 제공한다. 목록에서 확인되지 않는 ID는 404/noindex이며, 등록은 되어 있어도 진행·예정 팝업이 모두 사라져 목록에서 빠진 장소는 같은 제한을 받는다. 공개 API만으로 이 경우의 장소명·주소를 복구할 수 없다. 관리자 API나 임의 데이터를 사용하지 않는다.
- 일시적인 조회·응답 오류는 503/noindex 및 Retry-After 60으로 처리한다. 직접 접속·새로고침도 동일한 SSR 흐름을 사용한다.
- 공통 default 레이아웃과 웹 여백을 유지한다. 배너는 PC 2.5:1·모바일 16:9·radius8이며 H1·주소는 하단 그라데이션 위에 표시한다. 팝업은 PC 2열·모바일 1열, 포스터 3:4·radius6·텍스트 간격12px·제목 1줄 말줄임이다. 중복 장소 정보·길찾기 섹션은 제거되어 있다.
- 공개 응답에는 장소 운영시간과 팝업별 `locationDetail`이 없으므로 표시하지 않는다. 이를 채우기 위한 N+1 상세 요청이나 영업시간 추정은 추가하지 않았다.
- 목록과 상세의 3분·날짜 변경 갱신, 이미지 오류의 60초 경과·분당 1회 복구 기준을 유지한다. 기존 캐시 유틸과 이미지 URL 생성은 변경하지 않는다.
- 장소명 기반 title·description·OG/Twitter를 공통 SEO composable로 설정하고, 기존 전역 canonical을 사용한다. 화면 브레드크럼에 대응하는 BreadcrumbList만 추가한다. 평점·운영시간·Event 데이터는 생성하지 않는다.
- 공통 공개 SEO 경로에 `/venues/{venueId}`를 추가하되 운영 호스트·Preview 정책은 유지한다. 사이트맵에는 기존 팝업 URL과 공개 장소 URL을 함께 넣는다. 기존 300초 TTL·분할을 유지하며 캐시 갱신당 장소 목록을 최대 한 번 추가 조회하고, 기존 30초 캐시를 공유한다. 장소별 조회는 없다. 원본 장애 시 기존과 같이 불완전한 성공 사이트맵 대신 503을 반환한다.
- 카드와 팝업 링크의 자동 prefetch를 끄고, 링크를 열 때 데이터를 조회한다. 단순 카드 노출로 여러 상세 페이지를 미리 조회하지 않는다.
- 이번 변경은 정적 코드 검토·diff 확인만 수행했다. 서버·API 요청·브라우저·테스트·타입 검사·빌드·배포는 실행하지 않았다. 직접 접속·404/503 응답·모바일 표시·실제 SSR HTML·사이트맵 포함 여부는 사용자가 확인해야 한다.

## 영문 slug와 태그 관리

- 카드·canonical·OG URL·BreadcrumbList·사이트맵은 공통 URL 유틸리티를 사용한다. 기존 Twitter Card에는 URL 필드가 없으며 title/description/image 구성을 유지한다.
- 매핑된 기존 ID URL은 두 공개 API 응답을 확인한 뒤 Nuxt 서버 `navigateTo(..., { redirectCode: 301 })`로 canonical URL에 이동한다. 클라이언트 이동에서도 replace를 사용한다. 이미 canonical인 경로는 이동하지 않아 루프를 막고, 없는 장소는 기존 404, 조회 장애는 503/noindex를 유지한다.
- 매핑이 없는 장소는 한국·일본 모두 기존 ID URL을 유지한다. slug는 소문자 영숫자·하이픈만 허용하며, 대문자 별칭 요청은 소문자 canonical로 이동한다. 중복 ID·중복 slug·별칭 체인을 가진 매핑은 적용하지 않고 ID URL로 fallback한다.
- 새 장소 매핑은 실제 공개 목록에서 ID·이름·국가·주소와 기존 키/slug 충돌 여부를 확인하고, 사용할 영문명을 확정한 뒤 `VENUE_SLUGS`에 한 쌍만 추가한다. 전체 목록을 확인하지 않고 일괄 생성하지 않는다. 공개한 쌍은 이름 변경 후에도 유지한다. API/DB에 새 필드를 만들지 않는다.
- 원본 태그는 Spring `PublicPopupService.venuePopups` → `responses` → `PopupResponse.tags`의 `{id, name}`이다. 기존 `normalizeVenuePopups`가 필드를 누락했던 부분을 보완했다. null/미제공은 빈 배열로 처리하며 잘못된 타입은 기존 오류 정책으로 처리한다.
- 기존 `/places`와 같이 API의 태그명을 사용하고 `TagChip`을 재사용한다. 기존 `languageCode=ko` 요청을 유지하며 일본 장소를 일본어 UI로 간주하거나 자체 번역을 추가하지 않는다.
- 카드 기간 아래 8px, 칩 간격 6px, 밝은 회색 배경·진한 회색 텍스트·둥근 칩을 SSR 출력한다. 한 줄에서 넘치면 말줄임/숨김 처리하고 태그가 없으면 영역을 숨긴다. 신규 요청·필드 제거는 없다.
- 태그 캐시는 v2, 사이트맵 캐시는 v4로 이름만 갱신해 이전 구조/URL의 캐시와 구분한다. 30초/300초 TTL·SWR·분할·이미지 갱신 기준은 유지한다.

## 이전 카드 선택 방식 — 현재 제거됨

현재 웹에는 재사용할 장소별 목록 라우트가 없고 전체 탭의 검색·필터 변경은 요청 범위 밖이다. 새 페이지를 만들지 않고 이 섹션 내부의 네이티브 대화상자로 해당 장소의 팝업을 표시한다.

- 카드 선택: 현재 `/places` 안에서 장소별 팝업 목록 열기.
- 팝업 선택: 기존 `/places/{publicId}` 상세 페이지로 이동.
- 닫기·Escape·포커스 복귀 및 조회 실패 시 재시도를 제공한다.

## 이전 실제 데이터 확인 결과 — 2026-10-26

2026-10-26 확인 시 운영 `GET /api/popups/venues?languageCode=ko` 응답은 정상 `{"venues":[]}`였다. **실제 표시 가능한 장소는 0개**이며 화면에 빈 상태 안내를 표시한다.

공개 응답만으로는 등록 장소 자체가 없는지, 주소가 정확히 일치하는 진행·예정 팝업이 없는지 구분할 수 없다. 임의 장소·이미지·개수를 추가하지 않았다. 실제 장소 카드와 대표 이미지의 최종 확인에는 기존 장소 API가 실제 장소를 반환해야 한다. 유효한 장소 ID가 없어 운영 장소별 팝업 API는 호출하지 않았다.

## 이전 모달 구현의 검증 기록

- `npm run typecheck`, `npm run build` 통과.
- 실제 빈 장소 응답으로 SSR 200·빈 상태 표시·장소 목록 요청 1회·장소별 요청 0회를 확인했다.
- 응답 정규화에서 주소 보존, ID 중복 거부, publicId 중복 제거, 진행·예정 날짜, 전체 개수 불일치·오류 처리를 확인했다.
- **별도 검증용 계약 응답**으로 PC 3장(너비 약 264.66px·간격 16px), 모바일 1장(335px), 이미지 비율, 스와이프, 유한 화살표, 모달, 상세 링크, 닫기·Escape, 404 안내, 캐시 재열기를 확인했다.
- 동일 검증에서 Hydration 완료 후 초기 브라우저 API 요청 0회, 장소 선택 시에만 조회, Hydration mismatch·미처리 예외 없음, 모바일 가로 넘침 없음을 확인했다.
- 검증용 응답은 제품 코드에 포함하지 않았다. 실제 장소가 채워진 운영 데이터 검증과는 구분한다.
